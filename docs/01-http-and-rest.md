# 01. HTTP: как телефон разговаривает с сервером

Представьте кафе: клиент делает заказ (HTTP-запрос), кухня его обрабатывает (backend), а официант приносит результат (HTTP-ответ). Телефон не подключается к PostgreSQL напрямую — он отправляет запрос FastAPI.

**Адрес** `http://localhost:8000/activities` состоит из протокола, адреса сервера, порта и пути. Метод говорит, какое действие ожидается:

| Метод | Пример | Смысл |
| --- | --- | --- |
| GET | `/activities` | Получить список, не меняя данные |
| POST | `/activities` | Создать новый объект |
| PUT | `/activities/{id}` | Заменить ресурс или идемпотентно установить состояние |
| PATCH | `/history/{id}` | Изменить часть данных |
| DELETE | `/favorites/{id}` | Удалить запись |

Сервер обычно возвращает **JSON**, HTTP-статус и заголовки. `200` — успешно; `201` — создано; `204` — успешно, но тело пустое; `404` — не найдено; `422` — FastAPI/Pydantic отклонил данные; `500` — внутренняя ошибка. `503` — сервис временно недоступен.

**Идемпотентность:** повтор `PUT /favorites/{id}` должен оставлять идею в избранном без дублей. Повтор `POST /activities` без дополнительной защиты часто создаст вторую запись. Это особенно важно при плохом интернете.

Пример ответа на `GET /health`:

```json
{"status": "ok"}
```

Проверка из терминала: `curl http://127.0.0.1:8000/health`. Но первые запросы удобнее отправлять через Swagger.

**Проверьте себя:** какой код должен вернуть `GET /activities/неизвестный-id`? Почему для добавления в избранное может подойти PUT, а не POST?
